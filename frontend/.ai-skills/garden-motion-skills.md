# Motion Showreel

Turn an idea into a short video focused on graphics, text, or UI animations, delivering both an MP4 and reconstructable source code.

**Principle**: The page exposes a deterministic `render(t)`. A script captures screenshots frame-by-frame, and ffmpeg synthesizes them into an MP4. Soundtracks and sound effects are synthesized in the code and share a timeline (`timeline.js`) with the visuals, enabling frame-accurate beat-syncing.

**Where do good films come from?**: Density of variation, motion texture, a memorable hook, and audio-visual relationship—these four usually determine the viewing experience. But exactly how things move and how much they move is determined by **style and content**. Not every video needs multi-camera setups, springs, and screen-filling sound effects. We only adhere to a few baselines globally (see "Baselines"), the rest are starting points for the model, not ceilings.

---

## Scope of Application

| User Wants | Use this Skill? |
|---|---|
| Product promos, motion portfolios, UI animations, dynamic typography / beat-syncs, Logo reveals, intros, looping GIFs | ✅ |
| Green-screen humans generated by video models + code-generated scenes, large text, and animations | ✅ Humans provided by user (`references/formats.md` Category H) |
| A multi-minute video with a spoken script or article, explained sentence-by-sentence | ❌ Use `web-video-presentation` |
| Web pages, landing pages, interactive prototypes, static visual mockups | ❌ Use `web-design-engineer` |
| Realistic human performances, live-action textures, editing existing footage, generating visuals directly via video models | ❌ |

**Duration**: Best suited for 5–60 seconds. Purely music-driven, narrator-less videos can go up to about 2 minutes (like the `mixed-media-era` retrospectives); for anything over 60 seconds, produce and review it in segments, and clarify the rendering and review costs with the user before starting. Videos requiring voiceover explanations fall outside the scope of this Skill.

## Opus Strengths and Default Pitfalls

- **Strengths**: Can mix Canvas, SVG/DOM, WebGL, Three.js in a single file, or even change mediums per segment; motion can be precisely calculated via formulas (closed-form springs, beat grids, sub-frame motion blur); audio and visuals read the same timeline; can autonomously "render stills → view images → modify" over long periods; strong aesthetic judgment—a simple "go all out" might produce something stunning.
- **Default Pitfalls**: Without constraints, visuals default to dark backgrounds, large centered text, all elements fading in simultaneously, purple-blue gradients with glow, and static camera; soundtracks default to A-minor four-on-the-floor, impact + crash on every downbeat, and a bell toll at the end, making several videos sound like the same song. Therefore, you must first find references (for both visuals and audio), and clearly write out the style and forbidden list. However, constraints shouldn't be rigid: the style and technique libraries in this Skill are starting points, ready to be modified, mixed, or customized as the theme demands.
- **What it does poorly**: Realistic humans, complex hands/fabric/hair, things requiring real physical accuracy, photorealistic products (unless the user provides models or images). For these, use stylized treatments or switch to a green-screen human + code scene division of labor.

## Workflow


```

0 Environment Check (Once)
1 Ask Everything Once ─── Skip what can be inferred from the request
2 brief.md ────────────── Benchmark → Use Case + Style → Reel Read → Beat Grid + Storyboard + Forbidden List
3 Style Frames ────────── 🛑 The ONLY pause point: Style set → 3 frames for 1 direction; Style unset → 1 frame for 3 directions
4 Production ──────────── timeline → shot-by-shot → still-frame self-check → determinism check → proxy → final cut
5 Audio (Optional) ────── Code synth / User track / Silent
6 QA & Review ─────────── Tech check (programmatic, MUST pass) + Review (list issues from images, pass to user for final call)
7 Delivery

```

Working directory: Create `<slug>/` in the user's current directory. Place all files inside it: `brief.md`, `index.html`, `motion.js`, `timeline.js`, `score.mjs` or `score.tone.js` (based on `--audio` scaffold choice), `build.sh`, `fonts/`, `assets/`, `audio/`, `qa/`, `out/`.

### Step 0: Environment

Run `sh <skill>/scripts/setup.sh` on first use: it installs Playwright and Chromium, then runs `check-env.mjs`. Requires Node 18+ and ffmpeg; if missing, tell the user how to install them, do not install system software for the user. Tools come with tests: `cd <skill>/scripts && npm test`.

### Step 1: Ask Everything Once

Ask using **one single message**, maximum 5 questions. Skip what's already answered in the request. If the user says "you decide", use all default values and note this in the brief.

| What to ask | Default value |
|---|---|
| Theme and assets: logo, product screenshots, copy, brand colors, fonts | Use only facts provided by the user; don't invent features, data, or clients |
| The one sentence or visual the audience should remember | Extract from the theme |
| Duration, aspect ratio, platform | 15s · 1920×1080 · 30fps; use 1080×1920 for vertical platforms; UI motion can use 60fps |
| Style: Any specified style, reference video, or screenshots? | If none, provide 3 directions in Step 3 to choose from visually |
| Audio: Silent / Code synth / You provide a track (must be commercial-use) | Code synth |

- If the user provides a reference video: First run `inspect.mjs sheet <ref> --cells 30` to see the whole picture, `inspect.mjs grid <ref> --strips` to measure edit points and the beat grid they fall on (BPM candidates, steps per segment, continuous frames per transition), `inspect.mjs heat <ref>` to see where and how much motion happens per segment. Write the measured numbers into the brief's benchmark section. Only learn structure and techniques, do not copy assets.
- If the user provides a track: First run `audio.mjs beats <track> --out <slug>/audio/beats.json`.
- Verify any product, brand, or technical terms that need to appear in the visuals if unsure.

**Hands-off Mode**: When the user says "go all out", "do your thing", "surprise me", or only gives a theme without other requirements, enter hands-off mode: only adhere to baselines and the technical pipeline. You judge the style, structure, and techniques. You can entirely skip the pre-made style library. You must still write a brief (this is how you keep your own creativity controllable and reproducible), and still provide 3 directions in Step 3.

### Step 2: brief.md

**Find references first**: Before starting, pick 1-2 benchmark works for this video (this theme + this use case). They can be movie intros, ads, games, motion portfolios, or design movements. Write down "What to learn" (composition, pacing, camera grammar, color logic, music structure) and "What not to learn" (characters, specific shots, melodies, logos, font files) in the brief. References raise the ceiling better than any rules.

**Brainstorm three candidate structures**: e.g., a journey, a before/after comparison, a countdown, a morph, a continuous single-take. Write them down in 2-3 lines each, pick one, and state why. The first idea that pops up is usually a cliché for that style.

Choose **Use Case** and **Style** separately:
- For Use Case (what to film, structure to use), look at `references/formats.md`, read only the relevant section.
- For Style (what it looks like, how it moves, audio), check `references/styles/INDEX.md` first, then **read ONLY the 1-2 selected style files**. Styles can be used as-is, modified (swapping 1-2 rules), mixed (one primary, one secondary, or switching mediums by segment), or customized via `styles/_template.md`. Keep style rules constant, but draw the story, camera, and structure from the user's theme, don't inherit them from other videos. Every style file has "Recognition Signals" and "The Most Cliché Version" sections: pick 2-3 signals based on the theme (at least one outside the cliché list), and specify in the brief which clichés were flipped, or why they were kept. If a user picks a style, they want it instantly recognizable; 2-3 signals are enough.
- Pull from `references/craft.md` (technique library) as needed.

Write the brief according to `references/brief-template.md`, core is:

```yaml
Reel Read:
  format: [Use case, type from formats.md]
  benchmark: [Benchmark work · What to learn · What not to learn]
  structure: [Three candidate structures → Which chosen, why]
  style: [Style from styles/ (including tweaks), mix plan, or custom rules]
  signals: [Which 2-3 recognition signals chosen, why; which clichés flipped]
  takeaway: [The one sentence/visual to remember]
  hook: [What happens in the first 1 second]
  signature: [Memory point/Hook: At what second, what technique]
  palette / type / motion / camera / texture: [Specific values based on chosen style]
  sound: [Silent / Synth (audio benchmark, groove, harmony, instrumentation, curve, see sound.md Sec 2) / User track (BPM, drop)]
  forbidden: [Forbidden list for this video]

```

Then, write the **Beat Grid + Storyboard** in the brief: Set BPM and measure count first, one line per shot, specifying `Time Signature Range | Visual (including exact copy) | Motion | Camera | Audio | Transition`.

Even if the user just says "go all out", you must translate it into these specific constraints, otherwise the result is a gacha roll.

### Step 3: Style Frames (🛑 The ONLY pause point)

Create project: `sh <skill>/scripts/scaffold.sh <slug> [--audio synth|tone|layer|none]` (defaults to synth = tier 1 synth; only copies selected score, `build.sh` `AUDIO=` is set accordingly). The starter is only to verify pipeline works, visuals and copy MUST be replaced. Write `timeline.js` first.

**A. User has finalized style** (or gave clear references):

1. Build the hook frame, signature/memory point frame, and ending frame using real code, applying final colors, fonts, and copy.
2. `render.mjs <slug> --still 0.6,7.2,14.5 --sheet`, review yourself first, fix obvious issues before sending. If the signature heavily relies on motion, render a 2-3 second proxy clip (`--start --duration`).
3. Send the Reel Read summary, storyboard summary, and style frames to the user, ask "Is this direction correct?".

**B. User hasn't finalized style (including Hands-off Mode)**: Provide **3 distinct directions**, rules in `styles/INDEX.md`:

* A fits theme/brand closely, B uses a different visual language (from another group), C is bold (custom, mixed, or structurally daring; at least one direction must not be a pre-made library style).
* Write a mini Reel Read (style, benchmark, signature, music direction, 3-5 lines) for each direction, and render **one** representative keyframe using real code. Keep pages for all three in the same project, toggled via `?dir=a|b|c`. B and C only serve this single keyframe and don't need to be fully playable.
* `render.mjs <slug> --directions a,b,c --at 14.5,2,0` to render all three at once, stitch into a labeled `qa/directions.png`, send to user, ask "Which one, or how to mix them?".

In both cases, **actually wait for the user's reply** before starting production. If the user explicitly waived confirmation, pick one, state the reason, self-check, and proceed; provide the unselected directions at delivery (case B attach `qa/directions.png`, case A write one sentence on the other two possibilities) so the user can still swap if they return.

### Step 4: Production

Read `references/stack.md` before producing (page contracts, determinism, tech pitfalls). Check `references/recipes.md` for ready-made implementations.

1. Write all timestamps into `timeline.js`, import into page and `score.mjs`. Write shot list into `SHOTS` (QA will report motion per shot), deliberate holds into `HOLDS` (e.g. final freeze `[[b(36), DUR]]`), downbeats needing breathing room into `DROPS`; QA tools will read these. For beat-synced transitions, use `revealOn(beat, transitionDuration, revealPoint)` to reverse-engineer the start time so the new frame's reveal hits the beat.
2. Produce shot-by-shot. Render start, middle, and end stills for each shot; use `inspect.mjs strip` to check fast motion continuous frames.
3. Run determinism check: `render.mjs <slug> --determinism`, fix if it fails.
4. For videos >30s or slow renders, output a low-res proxy first: `--size 960x540 --out out/proxy.mp4`.
5. Final output: Set `FPS`, `SIZE`, `AUDIO`, `LOOP` at the top of `build.sh` according to the brief, then run `sh <slug>/build.sh`. It will build the music, run determinism check (without outputting video), render, run text bounding box checks (only outputs review materials, doesn't block build), and finally run technical QA using the same specs (duration taken from `timeline.js` `DUR`). Add `--subframes`, `--dpr`, `--grain` as arguments as dictated by style. These multiply render time, so quote ETA before rendering.

**Hard Rules**:

* Visuals depend ONLY on t: No `Math.random`, `Date.now`, rAF, timers, CSS animations. Do not save state between frames.
* Set `READY = true` ONLY after all fonts and assets load; self-host fonts inside the project.
* Derive layouts from `stageSize()` width/height, don't hardcode pixels.

### Step 5: Audio (Optional)

See `references/sound.md`. Audio direction (benchmark, groove, harmony, instrumentation, curve) is set in the Step 2 brief; write according to it. Pick a tier based on style:

| Tier | Uses | Suited for |
| --- | --- | --- |
| Tier 1 · Built-in Synth | `score.mjs`, Node synths (drums, claps, bass, pads, plucks, marimba/celesta/kalimba, organ, vocal pads, FM, ambient noise, SFX, sidechain, reverb, lo-fi processing), zero deps | Electronic, UI, Chiptune, Ambient, Lo-fi, Handmade/Toys, most motion videos |
| Tier 2 · Tone.js | `score.tone.js`, offline Tone.js render in headless browser: sampled instruments (`audio.mjs samples salamander` downloads CC BY piano), convolution reverb, richer synths & FX | Styles needing acoustic instruments, spatial depth, cinematic feel |
| External Track | User provided music (own, licensed, or AI-generated) | User already has music |

* Build: `audio.mjs build <slug>/score.mjs` or `score.tone.js`, outputs -14 LUFS `audio/music.wav`.
* User track: Run `audio.mjs beats` first (auto-uses librosa if available), align timeline, then `S.load()` in score to layer SFX.
* Silent: Skip this step.

You cannot hear the audio, so run `audio.mjs check` after every build to view metrics and charts. If `DROPS` are defined in `timeline.js`, it measures the dip in the half-beat before each drop and the spike on the drop, throwing a WARN if there's no "breathing room".

### Step 6: QA & Review

**Technical QA**: Programmatic. Failures block delivery.

```bash
node <skill>/scripts/inspect.mjs qa <slug>/out/final.mp4 --out <slug>/qa/final \
  --expect-size 1920x1080 --expect-fps 30 --expect-duration 16 --audio required   # Use --audio none for silent; add --loop for looping

```

Checks decode, dimensions, frame rate, duration, frame count, audio tracks, black frames, loudness, true peak, and loop seams (if needed). Exit code is 1 if any FAIL occurs; MUST be fixed. Unpassed specs map to `NOT CHECKED`, which doesn't count as passing. `build.sh` automatically passes specs. The render tool itself refuses to output files with wrong frame counts.

**Review**: For human judgment, not programmatic. Review extracted frames, mobile frame extracts, holds (declared `HOLDS` marked deliberate, others need check if dead air), cuts, motion/flashes by shot, text bounding box overlays (`qa/text-*.png`), audio charts. Write observations and top 3 severe issues using the `references/review.md` review sheet. Verify data/number consistency if present. Only re-render flawed sections after fixing, then output full video, logging the process in `qa/review_log.md`. If host supports sub-agents, dispatch a fresh agent to review these materials and list issues (review.md "Independent Review").

Review conclusions are references for the user, **they do not replace the user watching it themselves**. Mark N/A for inapplicable items (e.g., A/V sync for silent videos), do not force a score.

### Step 7: Delivery

Tell the user:

* Paths to `out/final.mp4` and `out/poster.png` (poster: `render.mjs <slug> --poster <t>`).
* `brief.md`: Full structured prompt, can be reused.
* Tech QA results (all PASS), unresolved issues from review log, render time.
* How to rebuild (`sh build.sh`), how to alter just one segment.
* Third-party asset origins & licenses (fonts, user assets, tracks); remind user to double-check factual claims.

Spend a few minutes reviewing post-delivery: if a specific technique clearly elevated the video (with proof/metrics/comparisons), log it in `references/field-notes.md`; add a note to the used style's "Implementation Log" in `styles/INDEX.md`, log new weaknesses under "Pitfalls". Only log reusable methodologies; leave user assets/private info in the project.

## Baselines (All styles must follow)

1. **Factual Accuracy**: Product features, stats, and names come ONLY from the user or reliable sources. Mark uncertainties.
2. **Text Legibility**: Font sizes readable on mobile, hold times long enough to read (see craft.md Sec 7); no overflow, overlap, or clipping.
3. **Asset Licensing**: Logos, screenshots, fonts, and tracks must be cleared for use, list them on delivery.
4. **Technical Correctness**: Deterministic render, Tech QA fully passed, no black frames, ending cannot abruptly cut off (freeze frame or seamless loop).
5. **Style Consistency**: Selected style rules maintained start to finish, do not violate brief's forbidden list.

Beyond this, how much the camera moves, spring usage, SFX density, and pacing are dictated by style and content (see references/styles/ and craft.md).
